# Python 沙箱与安全执行：如何让用户代码不拖垮服务

股票策略平台有个高风险特性：用户提交的量化策略代码要在服务器上**真实执行**（回测）。用户代码可能是无限循环、疯狂申请内存，甚至是恶意的系统调用。安全执行是上线前必须解决的核心问题。

## 第一层：进程隔离

用户代码不在 Web 服务进程里跑，而是放进**独立子进程**。子进程崩溃、被杀、耗尽资源，主服务毫无感知。回测逻辑只在这个隔离进程里运行，与 API 服务物理隔离。

## 第二层：资源限制

光隔离还不够，进程可以吃光整台机器。我做了三层限制：

- **CPU**：子进程绑定 CPU 时间上限，死循环自动终止；
- **内存**：限制进程内存配额，超限即 kill；
- **文件/网络**：工作目录沙箱化，屏蔽危险系统调用。

```text
用户代码 → 沙箱进程（CPU/内存受限） → 结果或异常 → 回填任务结果
```

## 第三层：异步队列控并发

单机同时跑几百个回测会互相抢资源。任务统一进 **Celery 队列**，用 worker 并发数 + 任务超时兜底，保证任何时刻在跑的沙箱进程数量可控。

## 第四层：可观测

每次执行记录耗时、资源峰值、退出码。异常任务自动重试或标记失败，用户在前端能看到"回测失败原因"，而不是一个卡死的按钮。

## 一点反思

安全执行没有银弹，只有纵深防御：**隔离 + 限额 + 限流 + 观测**四层叠加。这也是我在实习里修复 SSO 认证绕过问题时的体会——安全永远是设计出来的，不是补丁补出来的。
