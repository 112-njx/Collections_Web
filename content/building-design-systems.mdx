# MySQL 索引、事务与 SQL 调优实战笔记

## 索引不是越多越好

最常见的坑是"见列就建索引"。实践中索引的选择遵循几条朴素原则：

- 区分度高的列放联合索引左侧（如 `status + created_at` 优于反序）；
- 覆盖索引能省回表，查询列表尽量与索引列对齐；
- 最左前缀要记牢：`(a, b, c)` 索引能服务 `a`、`a,b`、`a,b,c`，但跳过 `b` 直接查 `c` 就失效了。

## 事务与锁

- **隔离级别**：默认 RR（可重复读），但很多读多写少的业务用 RC 更合适，能减少间隙锁导致的并发阻塞；
- **锁粒度**：批量更新优先按主键排序再更新，避免死锁；`SELECT ... FOR UPDATE` 只锁真正要改的行；
- **一致性读**：长事务会撑大 undo log，能拆短就拆短。

## 慢 SQL 三板斧

1. `EXPLAIN` 看 `type`：尽量到 `range`/`ref`，出现 `ALL` 就要警惕全表扫描；
2. 看 `rows` 与 `filtered`：估算扫描行数，配合 `profile` 定位耗时阶段；
3. 排序与分组尽量走索引，`filesort`/`temporary` 出现时考虑调整索引或改写 SQL。

## 写在最后

调优的本质是**理解数据分布**。同样的 SQL，在 10 万行和 1000 万行的表上结论可能完全不同——先看数据，再谈优化。
